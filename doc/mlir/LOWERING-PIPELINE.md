# MLIR Lowering Pipeline

**Related:** [../MLIR-COMPILATION-OVERVIEW.md](../MLIR-COMPILATION-OVERVIEW.md)

---

## Overview

This document provides a high-level overview of the MLIR lowering pipeline, showing how ONNX models are transformed through multiple dialect levels to native GPU code. For detailed implementation specifications of each pass, see the individual documents in [`passes/`](passes/).

**Purpose of this document:**
- Understand the overall transformation flow
- See how @main signature evolves through stages
- Understand data flow (constants, dynamic shapes)
- Navigate to detailed pass implementations

---

## Pipeline Architecture

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  ONNX-MLIR   │────▶│ HIP Dialect  │────▶│ LLVM Dialect │────▶│ Native Code  │
│  (MorphiZen) │     │ (OnnxToHip)  │     │ (HipToLLVM + │     │ (LLVM JIT)   │
│              │     │              │     │  GenInterface)│     │              │
└──────────────┘     └──────────────┘     └──────────────┘     └──────────────┘
   tensor types         memref types        memref structs         DLL export
   return values        context param       array parameters       3 C functions
   onnx.Constant        hip operations      wrapper functions      (init/compute/
   onnx operations      hip.context         llvm operations         cleanup)
```

---

## Transformation Overview

### Stage 1: ONNX-MLIR (Input from MorphiZen)

**Input:** ONNX model file (`.onnx`)
**Output:** MLIR module with ONNX dialect, func, arith
**Generated by:** MorphiZen framework (existing)

**Key characteristics:**
- High-level ONNX operations (`onnx.Conv`, `onnx.Relu`, `onnx.Constant`)
- Tensor types with compile-time shapes
- Constants as `onnx.Constant` operations
- Functional style: return values
- Supports multiple inputs and outputs

**@main_graph signature at this stage:**
```mlir
// Multiple inputs, single output
func.func @main_graph(%arg0: tensor<1x3x224x224xf32>, %arg1: tensor<64x3x3x3xf32>)
  -> tensor<1x64x224x224xf32>

// Multiple inputs, multiple outputs
func.func @main_graph(%arg0: tensor<1x3x224x224xf32>, %arg1: tensor<1x1000xf32>)
  -> (tensor<1x1000xf32>, tensor<1x10xf32>)
```

---

### Stage 2: HIP Dialect (OnnxToHip Pass)

**👉 See [passes/OnnxToHip.md](passes/OnnxToHip.md) for implementation details**

**Major changes:**
- **Constants**: Extracted from inline → `llvm.mlir.global` (DLL `.data` section)
- **Operations**: ONNX ops → HIP ops (e.g., `onnx.Conv` → `hip.conv`)
- **Types**: `tensor<...>` → `memref<...>` (in-place semantics)
- **Signature**: Add context parameter, output argument, status return
- **Metadata**: Add module attributes (I/O counts, ranks)
- **Generated**: Constant management helpers

**@main signature at this stage:**
```mlir
// Single input, single output (simplified example)
func.func @main(%ctx: !hip.context,           // NEW: context parameter
                %input: memref<1x3x224x224xf32>,
                %output: memref<1x64x224x224xf32>)  // NEW: output parameter
                -> i32                         // NEW: status return

// Multiple inputs, multiple outputs
func.func @main(%ctx: !hip.context,
                %input0: memref<?x?x?x?xf32>,
                %input1: memref<?x?xf32>,
                %output0: memref<?x?xf32>,
                %output1: memref<?xf32>) -> i32
```

**Module-level changes:**
```mlir
module attributes {
  hipdnn.input_count = 1 : i64,              // NEW: metadata
  hipdnn.input_ranks = dense<[4]> : tensor<1xi64>
} {
  llvm.mlir.global constant @constant_0 ...   // NEW: extracted constants
  func.func @main(...) { ... }
  llvm.func @get_constant_count() -> i64      // NEW: helpers
  func.func @initialize_constants(...) -> i32
  func.func @release_constants(...) -> i32
}
```

---

### Stage 3: LLVM Dialect (HipToLLVM Pass)

**👉 See [passes/HipToLLVM.md](passes/HipToLLVM.md) for implementation details**

**Major changes:**
- **Wrappers**: Generate wrapper functions for MIOpen/hipBLAS calls
- **Signature**: Transform @main to use memref struct arrays (scalable I/O)
- **Types**: `!hip.context` → `!llvm.ptr`, memref → struct-by-value
- **Operations**: HIP ops → wrapper function calls
- **Dynamic shapes**: Wrappers extract dimensions at runtime from structs

**@main signature at this stage:**
```mlir
llvm.func @main(%context: !llvm.ptr,          // Context lowered to pointer
                %inputs: !llvm.ptr,           // NEW: Array of input memref structs
                %outputs: !llvm.ptr)          // NEW: Array of output memref structs
                -> i32

// Note: Supports arbitrary number of inputs/outputs via arrays
// The number is determined by module metadata attributes
```

**Critical transformation - wrapper generation:**
```mlir
// NEW: Wrapper encapsulates MIOpen complexity
llvm.func @hip_conv_wrapper(%ctx: !llvm.ptr,
                             %input: !llvm.struct<...>,   // Struct-by-value!
                             %weights: !llvm.struct<...>,
                             ...) -> i32 {
  // Extract RUNTIME dimensions (dynamic shape support!)
  %n = llvm.extractvalue %input[3, 0] : !llvm.struct<...> -> i64
  %c = llvm.extractvalue %input[3, 1] : !llvm.struct<...> -> i64
  // Pass runtime dimensions to MIOpen
  llvm.call @miopenSet4dTensorDescriptor(%desc, %type, %n, %c, %h, %w)
  llvm.call @miopenConvolutionForward(...)
}
```

---

### Stage 4: C Interface (GenerateInterfacePass)

**👉 See [passes/GenerateInterfacePass.md](passes/GenerateInterfacePass.md) for implementation details**

**Major changes:**
- **Generate**: Three C-compatible exported functions
- **inference_init**: Allocates context, creates handles, uploads constants
- **inference_compute**: Parses user tensors, loads runtime dimensions, calls @main
- **inference_cleanup**: Frees resources

**New exported functions:**
```mlir
llvm.func @inference_init(%out_state: !llvm.ptr<!llvm.ptr>) -> i32
llvm.func @inference_compute(%state: !llvm.ptr, %inputs: !llvm.ptr, %outputs: !llvm.ptr) -> i32
llvm.func @inference_cleanup(%state: !llvm.ptr) -> i32
```

**Critical: Dynamic shape support in inference_compute:**
```mlir
// Load RUNTIME dimension values from user's tensor_t.shape array
%dim0 = llvm.load %shape_ptr[0] : i64  // Runtime load!
%dim1 = llvm.load %shape_ptr[1] : i64
// Calculate RUNTIME strides
%stride0 = llvm.mul %dim1, %stride1 : i64  // Runtime calculation!
// Build memref struct with runtime values
%memref = [construct with runtime dims and strides]
```

---

### Stage 5: Native Code (LLVM Backend)

**Input:** LLVM dialect module
**Output:** Native DLL (`.dll` / `.so`)

**Steps:**
1. Translate LLVM dialect → LLVM IR
2. Compile LLVM IR → Object file
3. Link with HIP/MIOpen/hipBLAS → Shared library

**Exported C symbols:**
```c
int32_t inference_init(void** out_state);
int32_t inference_compute(void* state, span_t* inputs, span_t* outputs);
int32_t inference_cleanup(void* state);
```

## Key Transformations Summary

| Aspect | ONNX-MLIR | HIP Dialect | LLVM Dialect | Native Code |
|--------|-----------|-------------|--------------|-------------|
| **Operations** | `onnx.Conv` | `hip.conv` | `llvm.call @hip_conv_wrapper` | MIOpen calls |
| **Types** | `tensor<...>` | `memref<...>` | `!llvm.struct<...>` | C pointers |
| **Constants** | `onnx.Constant` | `llvm.mlir.global` | `.data` section | GPU memory |
| **@main params** | N input tensors | context, N inputs, M outputs | context, input array, output array | — |
| **@main return** | M output tensors | `i32` status | `i32` status | — |
| **I/O structure** | Function params/returns | Separate memref params | Array parameters | `span_t*` arrays |
| **Interface** | — | — | 3 LLVM functions | 3 C exports |
| **Context** | None | `!hip.context` | `!llvm.ptr` | `void*` |
| **Dynamic shapes** | Compile-time rank | Compile-time rank | Runtime extraction | Runtime |

## Data Flow Through Pipeline

### Constant Lifecycle

Constants are transformed at each stage to enable efficient GPU execution:

```
Stage 1 (ONNX-MLIR):    onnx.Constant dense<[...]> : tensor<...>
                        └─ ONNX constant operations in @main
                              ↓
Stage 2 (OnnxToHip):    llvm.mlir.global constant @constant_0(...)
                        └─ Extracted to module-level globals
                              ↓
Stage 3 (HipToLLVM):    llvm.mlir.addressof @constant_0
                        └─ Referenced in initialize_constants
                              ↓
Stage 4 (Compilation):  DLL .data section (embedded in binary)
                              ↓
Runtime (init):         hipMalloc + hipMemcpy → GPU memory
                        └─ Uploaded once during inference_init
                              ↓
Runtime (compute):      hip_get_constant(ctx, index) → GPU pointer
                        └─ Retrieved and used in @main
```

**See:** [CONSTANT-MANAGEMENT.md](CONSTANT-MANAGEMENT.md) for detailed lifecycle documentation.

### Dynamic Shape Flow

Dynamic shapes are supported by deferring dimension value resolution to runtime:

```
┌─────────────────────────────────────────────────────────────────┐
│ Compile Time: Rank is known, dimension values are symbolic     │
└─────────────────────────────────────────────────────────────────┘
                              ↓
         Stage 2-3: memref types use compile-time ranks
                 (e.g., memref<?x?x?x?xf32> = rank 4)
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│ Runtime: User provides actual dimension values                  │
└─────────────────────────────────────────────────────────────────┘
                              ↓
  inference_compute: Load from tensor_t.shape
      shape[0] = 2    ─┐
      shape[1] = 3     ├─ RUNTIME values loaded from memory
      shape[2] = 256   │
      shape[3] = 256  ─┘
                              ↓
  Calculate strides: [196608, 65536, 256, 1]  ← Runtime arithmetic
                              ↓
  Build memref struct: {ptr, ptr, offset, sizes[4], strides[4]}
                       └─ sizes and strides are RUNTIME values
                              ↓
  @main receives memref struct arrays
                              ↓
  Wrappers extract dimensions:
      %n = llvm.extractvalue %input[3, 0]  ← Load runtime value
      %c = llvm.extractvalue %input[3, 1]
                              ↓
  MIOpen calls with runtime dimensions:
      miopenSet4dTensorDescriptor(desc, type, %n, %c, %h, %w)
```

**Key insight:** Rank (number of dimensions) is compile-time, but dimension *values* are runtime.

**See:** [../DYNAMIC-SHAPE-DESIGN.md](../DYNAMIC-SHAPE-DESIGN.md) for comprehensive design.

## Pass Dependencies and Prerequisites

Each pass builds on the output of previous passes:

```
┌─────────────────┐
│  OnnxToHip Pass │
├─────────────────┤
│ Generates:      │
│  • @main (HIP)  │
│  • Constants    │
│  • Helpers      │
│  • Metadata     │
└────────┬────────┘
         │
         │ Requires
         ▼
┌─────────────────┐
│ HipToLLVM Pass  │
├─────────────────┤
│ Generates:      │
│  • Wrappers     │
│  • @main (LLVM) │
│  • Lower helpers│
└────────┬────────┘
         │
         │ Requires
         ▼
┌──────────────────────┐
│ GenerateInterfacePass│
├──────────────────────┤
│ Generates:           │
│  • inference_init    │
│  • inference_compute │
│  • inference_cleanup │
└──────────────────────┘
```

**Prerequisites for GenerateInterfacePass:**
1. @main with signature: `(context, inputs, outputs) → i32`
2. Module metadata: `hipdnn.input_count`, `hipdnn.input_ranks`, etc.
3. Constant helpers: `initialize_constants`, `release_constants`, `get_constant_count`
4. Context layout: Known struct fields for handles and constants
5. Tensor interface: `tensor_t` with `data`, `shape`, `rank` fields

**See:** [INTERFACE-DESIGN.md](INTERFACE-DESIGN.md) for complete prerequisite specifications.

## Key Design Principles

1. **Progressive lowering**: High-level semantics → low-level implementation across stages
2. **Explicit state management**: Context/state passed explicitly (no hidden globals)
3. **Dynamic shapes from Day 1**: Rank is compile-time, dimensions are runtime
4. **Two-layer architecture**:
   - External: C interface (`inference_*`) for users
   - Internal: MLIR functions (`@main`, helpers) for optimization
5. **Pattern-based conversion**: Uses MLIR's rewrite framework for extensibility
6. **Inline lowering**: Operations lowered inline in @main (not library calls)
7. **Wrapper encapsulation**: Complex MIOpen APIs hidden in generated wrappers
